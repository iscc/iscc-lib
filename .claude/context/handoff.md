**Issues found:**

- **Filed as a `normal` `[review]` issue with HUMAN REVIEW REQUESTED** — "Freeze-rule ordering
    diverges from iscc-core on sequences". Stripping unassigned code points *before* normalization
    changes adjacency and therefore unblocks contextual transforms that `iscc-core` (which removes
    them *after* NFKC, via the category-`C` filter) still blocks. Measured this review, all three
    are new since iter 133 and persist even when both sides run identical Unicode 16.0 data:
    - `text_clean("e\u{0378}\u{0301}")` → `U+00E9`, reference `U+0065 U+0301` (canonical composition)
    - `text_clean("\u{1100}\u{0378}\u{1161}")` → `U+AC00`, reference `U+1100 U+1161` (jamo)
    - `text_collapse("\u{391}\u{3A3}\u{378}\u{392}")` → `…σ…`, reference `…ς…` (Rust `to_lowercase`
        evaluates `Final_Sigma` against the *stripped* context)
- This is a consequence of the approved design, not a defect — no alternative ordering keeps
    table-version invariance. What needs a human ruling is spec **wording**: criterion 4's
    "output-equivalent to uniform Unicode 16.0.0 tables" is false as literally stated (a
    per-code-point sweep passes and gives false assurance), the accepted-divergence paragraph does
    not cover this class, and the upstream proposal must specify pre-normalization removal or
    `iscc-core` will still disagree after adopting the rule. Rationale for merging anyway is in
    `decisions.md`
- Non-blocking: `is_c_category` / `is_cmp_category` keep their `GeneralCategory::Unassigned` arms
    (per Not-In-Scope) which are now unreachable in practice for both public functions. Coverage is
    unaffected (both still report 100%), so this is a note, not debt to file.

**Codex review:** Clean — "the Unicode 16.0 freeze filter is correctly applied before normalization

**Next:** Step (b) of the Unicode plan — **boundary conformance vectors**. The three boundary cases
(U+1FAE9 retained, U+113C5 decomposing, U+20C1 stripped) are all *single* code points, so they are
unaffected by the open sequence-ordering question and can proceed while that is with Titusz. Two
scoping decisions belong to define-next:

1. **Where the vectors live.** `crates/iscc-lib/tests/data.json` and its 4 sibling copies are
    vendored verbatim from `iscc-core` — adding project-specific vectors there makes future
    upstream refreshes a merge exercise. Recommend a separate fixture file (e.g.
    `unicode16_vectors.json`) with its own loader, sync'd across bindings the same way `data.json`
    is.
2. **Slice it.** Eleven binding suites in one step blows the file budget. The Rust core suite plus
    the fixture format is a clean first slice; the Rust-backed bindings (py, napi, wasm, ffi, jni,
    rb, uniffi, dotnet, cpp, swift, kotlin) all inherit the filter automatically, so their slices
    are mechanical. `packages/go` is the exception — it is an independent implementation on Unicode
    15.0 tables and needs either a vendored 15.0→16.0 delta or a documented skip (issue point 3).

Step (a2), the full-code-space differential sweep, should wait for the spec-wording ruling — its
acceptance criterion is exactly the sentence under review.
