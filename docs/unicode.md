# Text Processing and Unicode

iscc-lib declares **Unicode 16.0.0** as its Unicode data version. This page explains why that
version is part of the output contract, how the *freeze rule* keeps `text_clean` and `text_collapse`
— and therefore Meta-Code, Text-Code, and the returned `name` / `description` fields — stable across
runtimes and dependency upgrades, and where known divergences exist today.

---

## Why the Unicode version matters

`text_clean` and `text_collapse` classify code points by Unicode general category. A code point that
is *unassigned* in one Unicode version falls into category `C` (specifically `Cn`) and gets
stripped; once a later Unicode version assigns it, the same code point may be retained instead. The
output of text normalization — and every ISCC unit derived from it — therefore depends on which
Unicode tables the implementation ships.

Without a declared version, upgrading a Unicode-table dependency could silently change the ISCC of
any text containing newly assigned characters. iscc-lib treats the Unicode data version as part of
the conformance contract, not an implementation detail.

## Declared version and freeze rule

The declared Unicode data version is **16.0.0**. It is enforced by a *freeze rule*: code points
unassigned in Unicode 16.0.0 are removed from the input **before** any normalization or category
lookup, in both `text_clean` and `text_collapse`.

The removal uses a vendored table of unassigned ranges — **731 ranges covering 819,533 code points**
— generated by the checked-in script `scripts/gen_unicode16_unassigned.py` from
`unicodedata2==16.0.0`.

Because removal happens first, the result does not depend on which Unicode tables the underlying
crates ship: characters assigned after 16.0.0 are stripped regardless of what a dependency's tables
say about them. The `unicode-general-category` crate (16.0 tables) and the `unicode-normalization`
crate (17.0 tables) may be upgraded freely without changing output.

## Boundary behaviour

The four single-code-point vectors below pin the Unicode 16.0.0 boundary. Each input has the shape
`"a?b"` where `?` is the code point under test:

| Code point | Unicode 16.0 status         | `text_clean("a?b")` | `text_collapse("a?b")` |
| ---------- | --------------------------- | ------------------- | ---------------------- |
| `U+1FAE9`  | assigned (category `So`)    | retained            | retained               |
| `U+113C5`  | assigned (category `Mc`)    | retained            | `"ab"` (mark stripped) |
| `U+20C1`   | unassigned (Unicode 17 add) | `"ab"`              | `"ab"`                 |
| `U+A7F1`   | unassigned (Unicode 17 add) | `"ab"`              | `"ab"`                 |

`U+1FAE9` is the emoji 🫩 (FACE WITH BAGS UNDER EYES), added in Unicode 16.0; `text_collapse` keeps
it because symbols (`So`) survive the category filter. `U+113C5` is the Tulu-Tigalari vowel sign 𑏅,
also added in 16.0; `text_clean` keeps it, while `text_collapse` drops it because marks (`M`) are
filtered. `U+20C1` and `U+A7F1` are assigned only in Unicode 17, so the freeze rule strips them in
both functions — even though the normalization dependency already ships Unicode 17 tables.

These vectors are checked into the repository as `crates/iscc-lib/tests/unicode_boundary.json` and
exercised by the Rust test suite.

## Cross-implementation consistency

All 11 native bindings — Python, Node.js, WASM, C FFI, Java, Ruby, C#, C++, Swift, Kotlin, and the
Rust crate itself — wrap the same Rust core, so they agree by construction. Two divergences are
known today:

!!! warning "iscc-core on CPython ≤ 3.13"

    The Python reference implementation [iscc-core](https://github.com/iscc/iscc-core) inherits the
    Unicode tables of the running CPython interpreter. CPython ≤ 3.13 ships Unicode 15.1 tables, so text
    containing a character assigned in Unicode 16.0 hashes differently there. CPython 3.14 ships Unicode
    16.0.0 tables and agrees with iscc-lib. Adopting the same freeze-rule architecture upstream is
    proposed in [iscc-core/issues/137](https://github.com/iscc/iscc-core/issues/137).

!!! note "The pure-Go package"

    The Go module under `packages/go` is an independent reimplementation, not a binding over the Rust
    core. It filters on Go's `unicode.C` range table — Unicode 15.0 in Go 1.26 (`x/text`'s Unicode 17
    tables are gated behind `//go:build go1.27`) — and does not yet implement the freeze rule. It
    therefore drops characters assigned after Unicode 15.0 that the native bindings retain. This is a
    current, tracked limitation, expected to narrow once Go ships newer Unicode tables.

## Practical guidance

- **ASCII and Latin text is never affected.** The freeze rule only touches code points that are
    unassigned in Unicode 16.0.0; every character in common Western, CJK, Arabic, Cyrillic, and
    other established scripts has been assigned for many Unicode versions.
- **Inputs that differ across implementations in practice** are those containing characters newly
    assigned in Unicode 16.0 — realistically the seven emoji added in that version (such as
    `U+1FAE9` 🫩) — when compared against `iscc-core` on CPython ≤ 3.13 or against the pure-Go
    package.
- **Inputs containing unassigned code points** (for example characters from Unicode 17 or later) are
    normalized identically by all native bindings on every runtime: the freeze rule strips them
    before hashing.
